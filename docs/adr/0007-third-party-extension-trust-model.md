# 0007-第三方扩展（含 service）的信任模型：靠审核与撤销，不做系统级沙箱

> **2026-09-23 客户端实施补充**：本地后端默认不启动，用户须在扩展权限设置中明确信任当前版本；manifest 版本变化后重新授权。撤销运行或网络权限会停止受托管服务并撤销代理令牌。子进程只继承运行所需系统环境变量，不继承宿主的云凭据、`NODE_OPTIONS` 等环境。界面明确告知文件读写、联网能力及无系统沙箱的边界。本轮未实现服务端人工复审流程或子进程树隔离；授权不等于代码已审核，也不能约束可信版本号下被替换的本地源码。

> **状态：已决策，待实施**（决策于「扩展市场开放给第三方开发者」设计讨论，2026-09）。

扩展分两类：**web**（iframe + 桥 API）与 **service**（宿主启动的 Node 子进程）。ADR 0008 让 web 扩展失去直接读取宿主数据的能力；但 service 子进程以**当前用户身份**运行，可读写全盘、可任意联网，且同一用户下的两个进程无法用 ACL 互相隔离（身份相同，DACL 无从区分）。系统级隔离手段确实存在——低完整性级别 + 数据目录 `NO_READ_UP` 标签（约 1.5~2 周，唯一可行的"读隔离"路径）、AppContainer（与本项目"本地反向代理转端口"的架构直接冲突，且无 Node 生产案例）、换运行时（重写生态）——本项目**决定均不采用**。

因此第三方扩展（尤其是 service 类）的开放，**完全依赖三道治理**：提交时声明能力、人工审查（AI 辅助）、事后撤销与用户可见的权限告知。随之确立四条不可放宽的纪律：

1. **service 扩展的每次版本更新都必须人工复审**，不得因"权限声明未扩大"而自动放行——恶意代码可以后加，而权限声明一个字节都不用改。web 扩展不在此限，可按既有规则自动放行。
2. **审查必须读得到完整代码与依赖**：沿用既有规矩，禁止闭包二进制、禁止运行期远程加载代码；否则"审过"没有意义。
3. **AI 辅助审查是队列环节，不是放行依据**：门禁跑完后附一份可疑点清单（含文件与行号、能碰到什么），供人决策。
4. **告知必须显式**：安装或首次启用时明确呈现"此扩展可读写你的文件并连接网络"，不得仅以权限标签一笔带过。这是平台在无沙箱前提下唯一能对用户兑现的承诺。

**被否方案**：低完整性 + `NO_READ_UP`（成本可接受但本轮不做，属可增量补上的技术债）；Job Object（0.5~1 天，只治理资源与生命周期，不构成安全边界，本轮亦不做）；AppContainer（架构冲突）；换用户运行（装机与卸载代价过高、单人项目不划算）。

**代价（明确接受）**：一次恶意的 service 扩展更新就可能造成用户数据泄露，防线只有"审得出来 + 下架得快"；写坏的扩展可以吃满 CPU/内存或残留进程，只能靠用户卸载与平台下架处理。将来若要补沙箱，低完整性路线**不推翻现有架构**，属增量改动，但届时需要把已上架扩展重新过一遍。

**落点**：以上纪律写进提审门禁与后台队列（更新必审、AI 报告、显式告知文案）；撤销链路复用 registry 的 `revoked` 机制。
